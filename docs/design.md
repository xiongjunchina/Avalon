日期：2026-09-30。面向朋友线下同桌、每人一台手机、微信内邀请制网页。本文的“已确认”来自本次对话；“实现默认值”是可调整的工程决策，不冒充截图原文。

### 2.2 标准流程（已确认规则，补充操作细节）

1. 入座人数等于设置人数、全员准备后，房主开局；服务器安全随机分配身份并保存5秒截止时间。全员同步倒计时，结束后才开放私密身份查看；刷新不重新计时或洗牌。全员点击“我已记住身份”后进入组队。
2. 当前队长按任务人数选队，可选自己，同时选择顺／逆时针发言方向。预选阵容实时同步给全员，提交队伍后进入讨论，讨论与总结仍可修改；队长发起投票后才锁定。发言方向作为界面提示，应用不传输讨论音频。
3. 全体玩家各投一次赞成、反对或弃权；收齐后按赞成多于反对判通过，弃权不参与比较，平票或全员弃权不通过。匿名模式仅公开是否已投和最终总票数，公开模式实时显示个人选择。通过后进入任务，否则计一次流局、轮换队长并重新组队。
4. 入选队员各提交一次成功或失败；蓝方服务端仅允许成功，红方可选成功或失败。收齐后只公布总票数，不公布个人出牌。7–10 人第四次实际任务需至少两张失败票才失败，其他任务至少一张即失败。
5. 三次任务失败，红方胜；三次任务成功，进入正常刺杀；刺客命中梅林红方胜，否则蓝方胜。正常刺杀阶段允许同桌玩家面对面讨论，只有刺客能提交最终选择。
6. 每次组队表决失败或实际任务结束后轮换队长。流局不推进任务编号，不改变任务人数及第四任务门槛。

|captainMode|seat_order|按座位循环；random_order 为开局随机排列一次后整局循环，座位不变|

所有设置只在等待阶段由房主修改；修改后清除全员准备状态，广播差异。开局复制不可变规则快照并记录规则版本。常用设置仅保存设置，不保存邀请链接和成员。

### 2.4 湖中女神

第2、3、4次实际任务结束后触发；首次持有人为首任队长在物理座位顺序中的上一位，与随机队长排列无关。持有人选择一位从未担任过女神的玩家，不能选自己。仅当前持有人得到目标蓝／红阵营，目标成为下一位持有人。查验对象及交接公开，结果仅当次查验者可见，并保留在其个人私密视野中。查验后进入独立的结果确认步骤：只有当次查验者查看并确认后才继续下一步骤；交接后的新持有人不能读取前人的查验结果。复盘中可展示查验事件和最终身份。

### 2.5 提前刺杀

依用户明确选择：第二次实际任务结束起开放，流局不计实际任务次数。每局最多一次；刺客发起后强制进入刺杀，命中梅林红胜，未命中立即蓝胜。

实现默认值：仅在两轮间的独立窗口发起，不允许在任务出牌、投票或查验进行中打断。第二次及以后实际任务结算，以及此后组队被否决后，若尚未终局则进入此窗口。刺客选择发起或跳过；其他玩家只见统一“轮间确认中”，不见刺客身份及个人确认状态。跳过仅关闭当前窗口，后续符合条件的窗口仍可发起。全体客户端均收到等形公共状态，动作权限私发。

### 2.6 事件优先级（实现默认值）

任务收齐 → 结算票数 → 若红方三败则立即终局 → 若蓝方三成则正常刺杀 → 若尚未决定胜负则女神查验 → 提前刺杀窗口 → 下一次组队。

组队被否决 → 累计流局 → 达5次立即红胜 → 若符合条件则提前刺杀窗口 → 下一队长组队。

终局后不再触发女神或提前刺杀；三成后的刺杀归为正常刺杀。中断局不算胜负，不能借中断撤销已经结算的输赢。

## 3. 页面与交互

首页：继续未结束房间、创建房间、通过房间码加入、个人中心；首次填写昵称并使用预置头像。资料修改不更改旧战绩快照。

玩法指南：主导航常驻入口，未登录也能查看。游戏规则与角色介绍分区，覆盖标准流程、胜负、5–10人配置、任务人数、房间设置、湖中女神、提前刺杀和八角色视野。通用人物插画不显示本局身份分配。打开时卸载对局面板并收起本人身份，房间连接保留，返回不会退出房间。

等待房间：邀请按钮、房间码、5–10个座位、网络连接状态、准备按钮、配置摘要。邀请码是随机不可预测令牌；短房间码作为便利入口配合限流。开局后不允许新玩家入座，只允许原成员重连。等待阶段增加房主控制的 acceptingNewMembers，默认 true；关闭后仅拒绝新成员，不清除准备状态。

对局主界面：任务进度、当前任务人数及失败门槛、流局计数与范围、队长、座位环、阶段操作面板、面对面讨论提示、公共记录。身份默认收起，点击单独查看，离开该面板即隐藏。不得通过页面源码或公共消息获取其他身份。

结算与复盘：获胜阵营、胜因、全员最终角色、逐轮队伍／表决汇总／任务票数／查验与刺杀事件。组队实名设置控制个人赞反展示；任务出牌人始终不公开。仅本局参与者可访问。收藏只记录引用，不创建公开分享副本。

个人中心：头像昵称、已完成局数／胜负／胜率、历史列表、收藏、角色及阵营统计、常用设置。胜率分母只含正常结算局；中断局单独标识，零局显示“—”。

线框：prototype/index.html。页面内所有内容均为演示数据，尚未实现网络、权限或真实对局。

## 4. 工程架构

选型：TypeScript；React + Vite 手机网页；Node.js + Fastify HTTP 服务；WebSocket 同步；PostgreSQL 持久化。版本在初始化时选稳定兼容版本并锁定，不在设计中臆定最新版本。规则引擎是独立纯逻辑包，不依赖 UI 或数据库。

备选比较：纯客户端组局实现快但无法可靠保护秘密和断线恢复，不采用；全套微服务独立扩展能力强但当前运维成本高，不采用；单体权威服务配数据库满足朋友房并保留拆分边界，采用。初期单实例运行，以数据库事务保证状态与操作一致性；多实例属于后续工作。

目录约定：apps/web、apps/server、packages/game-core、packages/contracts。服务端为客户端生成“公共视图＋本人私有视图”，不能将内部完整状态直接序列化返回。

不实现音视频通话、麦克风控制、录音或语音供应商适配；不需要 RTC 账号、令牌接口及通话费用预算。讨论由同桌玩家面对面进行。

## 5. 数据与接口契约

主记录（阶段6已实现）：users（昵称、预置头像、创建时间）；sessions（凭证摘要、有效期）；rooms（房主、设置、状态、版本）；room_members（用户、座位、准备状态）；games（规则版本、设置快照、内部状态、结果）；game_participants（不可变历史参与者索引）；command_receipts（用户、commandId、执行结果）；favorites（用户、对局唯一键）；setting_presets（用户、设置）。逐轮事件嵌入games.state.rounds及拓展记录，不另建game_events表。统计从已结算对局导出，避免独立计数器重复累加。

身份凭证采用服务器签发的随机不透明令牌，通过同站 Secure、HttpOnly Cookie 保存；数据库仅存摘要。访客会话默认30天滑动续期。WebSocket 同源握手验证 Cookie 和 Origin；变更 HTTP 接口检查 Origin 与 CSRF。

已实现HTTP接口：POST /api/sessions/guest；POST /api/sessions/refresh；GET /api/me；POST /api/rooms；POST /api/rooms/join；GET /api/rooms/:id。阶段6新增：PATCH /api/me、GET /api/me/stats、GET /api/me/games、GET /api/games/:id/replay、PUT/DELETE /api/me/favorites/:gameId、GET/POST /api/me/presets、DELETE /api/me/presets/:id；历史校验开局参与资格并使用游标分页。

WebSocket 客户端命令统一为 {commandId, expectedVersion, type, payload}，roomId 由已鉴权的连接路径确定。已实现type为 setAdmission、updateSettings、setReady、startGame、confirmRole、proposeTeam、startTeamVote、teamVote、missionVote、assassinate、requestAbort、voteAbort、returnToLobby、leaveRoom、inspectAlignment、confirmInspection、earlyAssassinationDecision。payload 由类型判别 schema 校验。

服务端消息包含 snapshot、commandResult、error、takenOver、left、roomClosed。snapshot.room 包含 id、version、房间资料及 game；game.self 为接收者私密视野，其余为允许公开的信息；每次状态变化后发送按接收者裁剪的全量快照，首版不做增量补丁。普通在线变化不改变房间版本；引发房主转交或取消中断请求时会更新版本。订阅及重连都重新鉴权并获取最新快照。

并发：同房间状态变更在数据库锁定事务中执行，状态、其中的逐轮记录与幂等结果一起提交；未来独立事件表也须同事务提交。先查相同用户的 commandId 幂等记录，再判断版本；重复请求返回原结果。版本过期返回 VERSION_CONFLICT 和最新视图，客户端不得自动重投不同选择。票一经接受即不可改，收齐前不推进。明确拒绝后解除等待并保留当前页面选择供重新确认；回执尚未收到时保留原命令编号等待确认。

统一错误码：UNAUTHENTICATED、FORBIDDEN、ROOM_FULL、GAME_IN_PROGRESS、WRONG_PHASE、INVALID_TEAM、INVALID_TARGET、NOT_READY、NOT_CAPTAIN、NOT_ON_TEAM、NOT_ASSASSIN、BLUE_MUST_SUCCEED、NOT_LADY_HOLDER、NOT_INSPECTOR、INVALID_INSPECTION_TARGET、GAME_ENDED、ABORT_PENDING、NO_ABORT_POLL、ALREADY_SUBMITTED、VERSION_CONFLICT、RATE_LIMITED、ROOM_CLOSED、JOIN_DISABLED、SERVICE_UNAVAILABLE；对用户显示可理解提示，不输出秘密状态或系统密钥。

## 6. 异常与隐私默认值

- 等待阶段离房可重新加入；房主主动离开则转交给最早加入的在线成员；无人在线时转交最早加入的剩余成员。房主断线保留60秒，再转交在线成员。无在线成员时保留房间，所有人离线24小时后清理；进行中标记中断而非判负。
- 对局中成员掉线保留座位，无机器人、替补或自动投票。只要必需操作未收齐便等待，重连可恢复。房主不是规则裁判，无权查看身份或代投。
- 首版没有自动行动倒计时，不因超时直接判负。长时间无法继续可由任一成员提议中断，当前在线成员全体同意才中断；在线状态由 WebSocket 关闭事件和服务端心跳判定；已确认断线立即显示离线，无响应连接通过心跳及45秒租约失效检测。60秒宽限用于房主转交，不用于计票。中断记录保留并显示原因。
- 同账号可查看多个页面，但仅最新连接具有操作权限，旧连接提示已在其他页面接管；重新连接不重复入座。同一用户同一时间只能占用一个未关闭房间的席位。
- 无音频采集与传输，不请求麦克风权限。页面切出或锁屏后返回时重新同步对局状态，秘密身份面板恢复为收起。
- 公共投票进度只显示已提交总数，避免提前暴露匿名投票人的行为；私有视野、任务个人选票、会话凭证不进入普通日志、错误上报或复盘。
- 任务出牌原始映射仅供活动对局判定，结算时从保存状态与持久事件中移除，只保留汇总；匿名组队表决同样移除个人选择。历史只有参与者可查。
- 访客身份不能限制一个人使用多个设备开多个账号；首版基于朋友互信，不宣称有实名防作弊能力。

## 7. 下一阶段依赖

独立于外部账号可完成：规则引擎、页面、房间服务、单机多客户端测试。微信内多人网页测试需要 HTTPS 测试地址及 iOS／Android 手机。生产域名、部署位置与费用在部署前落实；取消 RTC 不代表在线房间的服务器与域名必然免费。不以 localhost 检查替代真实手机验收。


## 8. 第三阶段实现

PostgreSQL 18.4 持久卷保存 users、sessions、rooms、room_members、command_receipts；SQL迁移版本记录于schema_migrations。第三阶段交付时仅实现等待房间；第四阶段通过002迁移增添games表。pg驱动每个事务固定一个数据库连接；房间行锁、用户锁和唯一约束控制并发。房间版本与回执在同一事务提交，成功提交后才广播。数据库故障返回SERVICE_UNAVAILABLE，无内存回退。

新增RoomView.acceptingNewMembers、setAdmission、POST /api/sessions/refresh。开关仅房主可改，不影响准备状态。等待房间还实现setReady、updateSettings、leaveRoom；对局命令在第四阶段接入，见下节。邀请令牌不出现在公共快照，仅成员查询接口返回。

会话通过已认证HTTP请求续期为30天并重设Cookie；前台每15分钟和页面重新可见时主动续期。WebSocket本身不刷新Cookie，每条命令校验会话，定时心跳也检查是否过期。HTTP使用Origin和自定义请求头CSRF防护，socket握手校验Origin及成员身份。HTTP开发的Secure关闭，HTTPS部署必须开启。

成员加入时间与递增序号用于稳定转交，座位顺序不充当加入先后顺序。在线连接ID与最后心跳保存到数据库；服务重启清除旧连接，但保留账号、座位、准备、设置和最后活动时间。重启后60秒内不转交房主；最后活动时间不会被重启刷新，因此不会无限延长24小时房间寿命。定时任务15秒扫描，转交和关房可能有最多一个扫描周期的延迟。

房主主动离开优先在线最早成员，否则选择最早剩余成员；被动离线60秒后没有在线候选时保留，成员后续上线再次检查。空房即关，全员离线24小时关房并释放成员约束，用户资料保留。关闭后的邀请和房间码返回ROOM_CLOSED；回执在关闭满30天清理。

单后端通过持有数据库咨询锁保证；所有权连接中断后需恢复数据库并重启后端。仅连接对象、心跳及发送队列在内存中，不存储权威房间状态。本阶段不提供多实例接管的透明容错。

前端传输对象保证一个连接尝试和一个未确认命令；重连仅重放原commandId，不创建新操作。旧回执不能解除新命令的等待；被接管的页面不会自动争抢。第四阶段已接入标准对局，拓展与个人中心继续后续开发。


## 9. 第四阶段实现（标准对局）

`packages/game-core` 实现纯函数状态机和按玩家投影；传入已鉴权的操作者与当前在线成员集合。服务器用 `crypto.randomInt` 的 Fisher–Yates 洗牌，角色与随机队长次序各洗一次。开局固化规则版本 `standard-no-lancelot-v1`、昵称／座位名册和设置。房主变更不改变游戏队长。

阶段依次为 `role_reveal → proposing → discussion → team_vote → mission`；流局回组队，第三次成功进入 `assassination`，终局为 `finished` 或 `aborted`。任务失败门槛、全部角色配置、有效票赞成多于反对与两种流局策略遵循上文。不会因断线代操作或超时判负。

002迁移新增 `games(id, room_id, ruleset_version, state, created_at, ended_at)`、`rooms.current_game_id`，房间状态扩展为 waiting／playing／finished／closed。内部状态 JSONB 包含角色和未收齐的票，只有服务端可读；客户端只能经鉴权接口获得裁剪结果。逐次组队和任务汇总嵌入 rounds，不另建空置事件表。个人战绩查询与收藏留待阶段6。

`game.self` 只有自己的准确角色、阵营、许可看到的红方成员或梅林候选，以及自身是否提交；绝不携带其他准确角色。派西维尔的梅林候选、队友列表按座位排列，不能从排序区分梅林与莫甘娜。全部角色仅在正常结束或中断后公开。每个 WebSocket 单独生成其玩家快照，HTTP 恢复和原成员再次加入亦使用相同投影。

新增命令：`startGame`、`confirmRole`、`proposeTeam`（成员列表、发言方向）、`startTeamVote`、`teamVote`、`missionVote`、`assassinate`、`requestAbort`、`voteAbort`、`returnToLobby`。沿用 commandId／expectedVersion、严格消息 schema、事务与房间行锁。最后一票的计数、阶段推进、结果和命令回执在一次提交内完成；失败不产生成功广播。并发票使用相同旧版本时只接纳先提交的一票，其余收到 VERSION_CONFLICT 后需在新状态重新确认，不能把旧选择自动用于下一轮。

新回执只保存规范化命令的 SHA-256 指纹及执行结果，避免保存明文选票副本；第三阶段旧回执仍支持比对原文。指纹用于重复命令识别，不是加密或针对数据库管理员的保密机制。任务个人选票收齐后立即清空，仅保留成功／失败票数；匿名组队同样清空个人选择，实名组队保留公开赞反用于复盘。活动状态和数据库备份仍应按私密数据管理。

开局仅房主可执行，要求人数齐、全员准备；等待所有成员各自确认身份后进入组队。玩法和接纳设置只在等待区可改。进行中不能离座、新成员不能加入，原成员可重连；结束后可退出。房主返回等待区时保留房间设置／接纳状态并清除准备，解除当前对局关联，原游戏记录保留。已完成对局不能再被中断覆盖。

房主可直接结束游戏，其他玩家可发起中止申请，由当前房主同意或拒绝。申请跨断线、进度更新与重启保存；房主同意后，同一事务内保存 host_ended 中断记录、关闭房间并清除全体房间成员。在线玩家收到 roomClosed 返回大厅，离线玩家重连也不再恢复旧房间。已完成局不受中止影响。全员离线24小时的进行中对局仍记为 offline_timeout 后关闭。

前端身份默认收起，在页面隐藏、断线、步骤切换或新局时收起。任务成功／失败控件两方外观一致，蓝方失败请求由服务器拒绝；不从某个控件是否存在泄露阵营。开局后页面显示任务格、流局数、当前队长和所需操作；结果公开角色与本局记录。第四阶段交付时湖中女神、提前刺杀不可启用；第五阶段已完整启用，见下节。


## 10. 第五阶段实现（湖中女神与提前刺杀）

新局规则版本为 `standard-no-lancelot-v2`。存量v1标准局没有拓展字段，仍按原标准流程恢复；不改动身份、设置或正在执行的阶段。games.state沿用JSONB，新增可选字段无需SQL迁移。后端仍单实例运行，拓展写入沿用房间行锁、版本校验与幂等回执，不引入客户端权威状态。

新增阶段 `lady`（选人）、`lady_reveal`（查验者确认结果）、`early_window`（私密轮间决定）；刺杀阶段保留 `assassination`，用 `assassinationMode: normal | early` 区分胜因。第2–4个实际任务结算且未终局时可进入女神；查验者确认后才进入提前刺杀窗口，或直接继续组队。进入这些轮间步骤前已轮换队长并推进到下个任务编号；页面另外明确显示“第几个任务后”的查验事件，流局不增加实际任务数。

内部 `lady` 保存当前持有人、历任持有人列表和查验记录。每条内部记录含 afterMission、inspectorId、targetId、team；公共投影只白名单输出前三项，绝不展开整个内部记录。只有对应查验者的 `game.self.inspections` 包含team，始终没有准确角色字段。持有人选中目标后立即交接，进入lady_reveal等待原查验者确认；下任持有人不能替别人确认或继承查验结果。

内部 `earlyAssassination` 保存 used 及每次窗口决策（已完成任务数、提案序号、skip／attempt），不记录公开操作者ID。窗口公共阶段／历史对所有玩家相同，`self.canDecideEarly`仅对刺客为true。相关按钮放在收起的私密身份面板中，普通玩家只见统一轮间提示。跳过后继续组队；后续实际任务结束或满足条件的流局可再次进入窗口。发起即used=true并强制进入刺杀，不能再跳过；命中为early_merlin_found，未命中为early_merlin_survived。已有的一致中断机制仍用于无法继续的对局，不能改写已结算结果。

拓展命令均只在其对应阶段接受：inspectAlignment {targetId}、confirmInspection {}、earlyAssassinationDecision {attempt}。服务器检查持有人／原查验者／刺客权限；前端隐藏按钮不代替服务器鉴权。女神结果和待确认阶段、刺杀决定及待选目标阶段均持久保存，断线不代操作。重复命令不会再次查验或新增窗口记录。

组合优先级与2.6节一致：三败／五流局立即结束；三成走正常刺杀，不再查验或提前刺杀；其他情况先女神，再提前窗口。同房下一局重新初始化拓展记录，不携带上一局的查验结果或使用状态。已结束对局的公开角色和拓展事件保留，个人历史入口待阶段6。


## 11. 第六阶段实现（个人中心与复盘）

`003_accounts.sql` 为 users 增加六种预置头像，新增 game_participants、favorites、setting_presets。已有v1/v2局从开局名单回填参与者；新局在开局事务内写入参与索引。退出房间、房间关闭和回执清理都不删除对局与参与索引。头像没有上传地址，不接外部图片服务；修改昵称只更新用户资料与当前房间名片，旧局名单保持不变。

历史和复盘仅接受 Cookie 对应用户，客户端不能传 userId 冒用身份。必须同时具有历史参与资格、ended_at 和 finished／aborted 状态；未结束、未参加和不存在统一返回 GAME_NOT_FOUND，HTTP 404。晚加入同一房间不获得旧局权限。HTTP变更接口沿用Origin／CSRF校验、会话滑动续期和no-store。

统计取已结束games，按参与者对应角色和最终获胜阵营聚合；没有独立加一计数器。completed只含winner非空记录，wins／losses据本人阵营判断，winRate为0–1比例；winner为空计入aborted，分母为0返回null，界面显示“—”。统计包含正常刺杀和提前刺杀，不以任务成功次数直接判个人胜负。

`GET /api/me/games` 支持 `limit`（默认10，上限50）、`cursor`、`favorites=true|false`。使用结束时间和UUID二元游标倒序，避免相同结束时间重复或遗漏；游标保留数据库时间戳精度，输入严格校验。收藏列表同样按结束时间排序。PUT收藏通过唯一键幂等，DELETE只移除本人引用，不删除对局。

复盘返回专用Replay白名单，不复用内部GameState。仅含名册、最终角色、规则快照、胜因、逐轮公开记录、女神查验／交接事件和提前窗口。即使存量记录含个人原始选票，匿名组队仍剥离ballots；任务结果只有successes／failures／passed。私有视野、原始任务映射、查验结果字段、连接和房间邀请不返回。实名组队只显示在完成表决后保存的公开赞反，未完成表决没有个人选择。

预设仅保存名称与通过settingsSchema的玩法；每人最多10个。同名POST更新现有记录，用户行锁序列化配额和同名并发写入。列表、保存和删除都按本人过滤。应用预设通过既有updateSettings命令发送实际设置，继续校验房主、等待阶段、版本和已占座位；成功后清除全员准备，不改变接纳开关。个人中心可编辑、保存、删除；房间等待区可保存当前玩法或应用预设。

前端顶部可在朋友桌与个人中心之间切换，房间连接保持；离开对局界面即卸载私密身份面板，返回后默认收起。个人中心有加载、空列表、失败重试、分页与收藏状态。结算页增加完整复盘入口。手机号、微信身份、会员、订单、兑换码和公开战绩分享均不实现。页面刷新会回到朋友桌并恢复账号与所在房间，个人中心栏目不写入URL。

## 13. 第七阶段本地部署与恢复

部署使用独立Compose项目：Caddy提供静态网页和同源HTTP／WebSocket入口，单个编译后Node后端连接PostgreSQL。仅网关映射本机端口；后端以非root、只读根文件系统运行。生产启动严格验证准确Origin、Cookie Secure和代理配置；公网Origin必须HTTPS。代理仅信任一跳，普通入口覆盖客户端转发地址，避免伪造地址绕过限流；ngrok专用转发边界见第15节。

启动和显式迁移在事务中取得数据库后端独占锁，活动实例下不能应用迁移。迁移成功后后端继续使用长期所有权锁。部署不新增业务表，仍为001／002／003迁移，旧角色和对局按原版本恢复。

备份使用pg_dump custom格式；同名清单记录SHA-256、字节数、数据库版本、迁移及镜像标识。恢复先校验，再在另一个空实例内单事务提交；拒绝原项目、活动应用目标、非空库、损坏备份及不匹配PG主版本。还原保留账号、会话摘要、房间、座位、准备、玩法、完整对局、历史参与资格、收藏、预设及命令回执；在线状态按连接重建。源库保持不变，恢复不自动迁移浏览器Cookie或复活过期会话。

本地HTTPS使用仅测试客户端信任的内部CA，不安装系统信任。ECS公网模板改用受信任证书、Secure Cookie、自动HTTPS及80／443入口；该模板目前仅解析验证，没有启动。当前先通过第15节的ngrok入口进行朋友内测。ECS资源、DNS／证书与续期、异地备份及真机多人体验仍为独立验收项。运行命令、升级恢复点及回退边界见[部署与备份指南](deployment.md)。

## 14. 发牌倒计时与玩法指南

新开局先处于 `dealing` 阶段，`games.state.dealEndsAt` 保存服务器生成的5秒截止时间。身份与开局快照在原startGame事务中只生成一次，原命令编号重试仍返回原回执。房间在此阶段已经playing，沿用设置和席位锁定；所有游戏动作均拒绝为DEAL_PENDING。掉线保留原局，不取消或重新分牌。

客户端RoomView包含serverTime；GameView仅在倒计时阶段包含dealEndsAt，不包含self或revealedRoles。页面按服务器时间与收到快照后经过的单调时间展示5→1，不依赖玩家手机时钟。页面倒数到0只显示同步提示，不自行解锁身份。

后端按持久化截止时间安排定时唤醒，重启时重建尚未结束的计时器。到期后releaseDeal取得房间行锁，重新检查阶段和时间，将状态改为role_reveal并增加版本号，同事务提交后才广播按玩家裁剪的身份。重复或并发唤醒只推进一次；写入失败继续保密并返回服务不可用提示，定时重试。不新增数据库表或迁移；既有非dealing的v1/v2对局继续原步骤。

指南的人数、角色组合与任务人数直接复用规则引擎常量，避免文案另维护一套配置；角色说明为纯通用内容，不读取个人角色。验证与界面截图见[倒计时与指南验证](countdown-guide-validation.md)。

## 15. Docker + ngrok 朋友内测

发布顺序调整为：本机Docker独立实例 → ngrok HTTPS朋友内测 → 真机完整对局验收 → 再购买阿里云ECS并接入已有域名。当前不修改DNS，不增加微信认证、语音或商业化功能。

`friends`实例使用独立项目、数据卷及镜像标签，通过`compose.ngrok.yaml`叠加配置，将Caddy监听地址设为本机8089的HTTP入口，应用Origin仍为实际ngrok HTTPS域名。公网TLS由ngrok终止；浏览器Cookie保持Secure、HttpOnly、SameSite=Strict；写入和WebSocket仍执行精确Origin及原有权限校验。数据库、后端和ngrok管理接口不向公网映射，原开发实例与8088试玩实例保留。

ngrok在转发地址链末尾加入实际客户端地址。专用网关保留该链，后端只取最近一跳；普通本机及ECS配置继续覆盖客户端转发头。专用配置不可直接改为公网监听；公网验收已覆盖伪造X-Forwarded-For不能绕过访客限流。

`deploy:tunnel:setup`校验HTTPS域名、端口和实例标识，生成私密环境文件并保留已有配置。`tunnel`提供start／stop／status；先核对本机agent中同名端点的域名、上游和关闭检查的设置，匹配时复用，不匹配时拒绝覆盖。停止只移除本应用端点，容器和数据保留；ngrok进程、Docker或电脑停止会中断访问。请求检查关闭，脚本与验收报告不打印凭证。

通过独立访客和房间执行公网HTTPS/WSS标准局、拓展局及接纳、恢复、回执和权限验证。自动化不代替微信真机验收；ngrok域名与将来正式域名的浏览器Cookie不能自动跨域迁移。操作步骤见[朋友内测指南](friends-test.md)，实际结果与待验收项见[内测验证记录](friends-test-validation.md)。


## 2026-10-17 朋友实测反馈修订

- 规则版本 `standard-no-lancelot-v3`。`teamVote.payload.approve` 接受 `true | false | "abstain"`，保留历史布尔票兼容；历史没有弃权计数时按0显示。新局采用有效票比较，任务牌仍始终匿名。
- `updateTeamDraft`：仅当前队长在揭牌/组队/讨论阶段可执行，允许0至本轮人数的不同成员；讨论时修改同一提案，不增加流局。`startTeamVote` 校验人数齐全后锁定，并保存 `teamVoteStartedAt`。草稿、公开投票进度与房主中止请求均在现有 JSONB 游戏状态持久化，不新增表。
- 投票弹窗自动打开，提供赞成/反对/弃权；可暂时收起并重新打开，未投仍计入等待。3秒后强调未投名单。服务端匿名投影不含个人票型，只有已投玩家ID；前端也防御性隐藏票型。
- 房主 `endGame` 直接结束；非房主 `requestAbort` 申请，房主 `voteAbort` 决定。沿用事务、版本号和幂等回执；成员解绑与结束记录原子提交。
